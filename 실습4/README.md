# 실습4 — 웹캠만으로 4인 실시간 AR 복싱, 그리고 조용한 실패들

MediaPipe Pose 상체 7노드로 복싱 모션을 읽고, Face Mesh 468 랜드마크로 **단안 3D 얼굴을 복원**해
아바타에 씌우는 브라우저 게임. 서버는 FastAPI + WebSocket, 렌더는 Three.js.

**웹에서 보기 →** https://kithhooni-commits.github.io/ds-practice/실습4/
**코드 →** https://github.com/gichul-hong/project-4 (`iter3/`)

## 결론 한 줄

가장 많은 시간을 잡아먹은 것은 **틀린 알고리즘이 아니라 아무 말 없이 꺼져 있던 기능들**이었다.
자동 조준은 대상 목록이 비어 있어 통째로 무효였고, 이동은 펀치 잠금에 막혀 6초에 **0 units**를
갔고, 3D 얼굴은 두개골 **안쪽**에 배치돼 어디서도 보이지 않았다. 셋 다 예외도 경고도 없었고,
**로직 하니스는 전부 통과**시켰다. 브라우저로 페이지를 실제로 띄우는 하니스를 만들고 나서야 잡혔다.

## 무엇을 만들었나

- **모션 인식** — 몸 기울임으로 전후좌우, 주먹 좌우 쓸기로 회전, 팔 궤적으로 잽/훅/어퍼컷 분류
- **단안 3D 얼굴 복원** — 입장 시 얼굴을 찍으면 그 자리에서 3D 메쉬로 복원해 아바타 머리에 씌운다.
  맞으면 그 자리가 눌리고 멍이 누적되며, HP가 떨어지면 코피가 나고 지친 표정이 된다
- **게임 규칙** — 최후 1인 생존, 분노 게이지(맞을수록 참) → 불꽃 오라 → 필살기
- **음향** — 오디오 파일 없이 Web Audio 실시간 합성. 데미지에 따라 소리가 달라진다

```bash

# 3) 실영상 채점 — 랜드마크 캐시를 쓰므로 opencv/mediapipe 불필요
```

`--version` 을 생략하면 `v1_baseline` 을 덮어쓰므로 새 실험은 반드시 태그를 준다.

되는 것과 안 되는 것은 `code/README.md` 9장 「웹에서 이어서 작업할 때」에 표로 정리돼 있다.

## 실영상 벤치마크

하니스는 **로직이 의도대로 도는가**를 본다. 하지만 "잽을 뻗었는데 잽으로 잡히는가"는
합성 궤적으로 알 수 없다. 그래서 사람이 90초 동안 정해진 순서로 복싱하는 영상에
**구간별 정답 라벨**을 붙여 채점했다.

| 지표 | 값 |
|---|---:|
| 정답 / 검출 | 29 / **59** |
| TP / FP / FN | 17 / 42 / 12 |
| 정밀도 | **0.288** |
| 재현율 | 0.586 |
| F1 | 0.386 |
| 기술 종류 정확도 | 0.235 |
| 좌우 정확도 | 0.471 |
| 타이밍 오차(평균) | 111.9 ms |

29개를 맞히려고 **59개를 쏜다.** 구간별로 보면 원인이 뚜렷하다.

| 구간 | 성격 | 검출 |
|---|---|---:|
| 직선 펀치 06~18s | 동작 | 5 |
| 훅 23~35s | 동작 | 17 |
| 어퍼컷 40~52s | 동작 | 15 |
| **풋워크 57~70s** | **비동작** | **9** |
| 숨고르기 4구간 | 비동작 | 2 |

**풋워크에서 9번 헛나간다.** 스텝을 밟으면 상체가 흔들리는데, 어깨 기준 손목 속도로는
이것이 뻗음과 구분되지 않는다. 훅·어퍼 구간의 17·15도 정답 대비 과검출이라 한 번 뻗을 때
여러 번 발사되는 것으로 보인다.

### 평가기가 판정 코드를 읽지 않는다

판정 튜닝을 여러 차례 바꾼 뒤 이 파이프라인을 돌렸더니 **한 수치도 안 바뀌었다.**
절대경로 한 줄을 빼면 결과 파일이 비트 단위로 동일했다.

원인은 평가기가 `punch_core.js` 를 읽는 대신 **상수를 자기 파일에 복사해** 갖고 있기 때문이다.
런타임을 어떻게 고치든 점수는 안 움직인다. 값을 직접 대조해 보니 펀치 상수 12개는 마침
일치했지만(그래서 위 점수는 유효하다), 같은 폴더의 전체동작 평가기는 자세·이동 상수 12개가
옛 값이고 필살기 판정이 통째로 없었다.

**포팅본은 조용히 어긋난다.** 이것이 판정 로직을 HTML에서 `punch_core.js` 로 분리한 이유이고
— 브라우저와 Node가 같은 파일을 쓸 수 있게 의존성을 0으로 만들었다 — 평가기를 Node 실행으로
바꾸는 것이 남은 작업이다.

## 한계

- **BiLSTM이 런타임에 연결되지 않았다.** 합성 데이터로 정확도 100%를 찍었지만 입력 규격이
  손 랜드마크 63차원이라 현재 Pose 7노드 파이프라인과 맞지 않는다. 실제 판정은 전부 규칙 기반이다.
  팀에서 실제 포즈 데이터셋(`collected_pose/`)을 모으기 시작했으므로 재학습이 다음 단계다.
- **단안 복원의 한계** — Face Mesh는 얼굴 **앞면만** 덮는다. 얼굴 테두리(FACE_OVAL 36점)를
  적도로 삼아 뒤통수를 생성해 닫힌 머리로 만들었지만, 뒤통수에 맞는 텍스처가 애초에 없다.
  테두리 픽셀에서 시작해 얼굴 안쪽 평균색으로 수렴시켜 색이 튀지 않게 이어 붙인 것이라
  **뒤에서 보면 머리 형태는 맞지만 머리카락 디테일은 없다.**
- **정밀도가 낮다** — 실영상 벤치마크에서 정밀도 0.288, 기술 종류 정확도 0.235다.
  게임에서 체감이 나쁘지 않았던 이유는 **과검출이 "잘 나간다"로 느껴지기 때문**이고,
  이 숫자는 그 체감이 정확도가 아니라는 것을 보여준다. 아래 벤치마크 절 참조.
- **조명·배경에 민감** — 어두운 곳에서는 랜드마크 신뢰도가 떨어져 팔 인식이 흔들린다.
