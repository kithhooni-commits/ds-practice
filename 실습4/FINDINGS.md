# 실습4 — 분석

웹캠만으로 4명이 실시간 대전하는 브라우저 AR 복싱. 여기서는 **무엇을 만들었나**보다
**무엇이 잘못됐고 어떻게 알아냈나**를 적는다. 그쪽이 실습에서 남는 것이었다.

---

## 1. 조용한 실패 네 건

기능이 "틀리게" 동작한 적은 거의 없었다. 대신 **아무 말 없이 꺼져 있었다.**
예외도 경고도 없고, 화면은 그럴듯하게 돌아간다. 네 건 모두 같은 형태였다.

### 1-1. 자동 조준이 통째로 무효였다

서버 타격 판정은 `dot(내 시선, 상대 방향) > 0.3` 이라 **조준이 곧 명중률**이다.
그런데 클라이언트는 상대 위치 표를 **상대가 보낸 패킷으로만** 채우고 있었다.

```js
const senderId = data.client_id;                 // 서버가 넣는 "보낸 사람" id
if (senderId && senderId !== clientId && ...) {  // ← 나 자신이면 스킵
  opponentPositions[senderId] = { ... };
}
```

혼자 접속해 테스트하면 돌아오는 패킷의 `client_id`가 전부 나 자신이라 이 표가
**영원히 비어 있다.** `findNearestOpponent()`가 `null`을 돌려주니 상시 정렬·펀치 스냅·
자동 접근이 **셋 다 조용히 무효**가 된다. 링에는 아바타가 그려져 있으니
화면상으로는 "상대가 있는데 안 돌아보는" 것으로 보인다.

**서버는 접속 여부와 무관하게 4명 전원을 타격 대상으로 두는데 클라이언트만 "접속한 상대"로
좁혀 보고 있었다** — 두 쪽이 아는 세계가 달랐던 것이 원인이다.

*고친 뒤 실측:* 옆(90°)에 선 상대에게 스냅 없이 `MISS`, 스냅 적용 시 `HIT`(HP 100 → 94).

### 1-2. 이동이 6초에 0 units

펀치 잠금(`PUNCH_LOCK`)은 펀치의 몸통 회전이 자세 신호를 오염시키는 것을 막는 장치다.
그런데 하한이 480ms였고, **실측 펀치 간격은 최소 0.20초 · 중앙값 0.25초**(서버 로그 533회)였다.
연타 중에는 잠금이 **한 번도 풀리지 않는다.** 게다가 잠금은 세 군데에서 이동을 죽이고 있었다.

```js
let mCand = "NONE"; if (!locked) { ... }   // (1) 새 상태가 안 생김
if (locked) mi = 0;                        // (2) 남은 강도까지 0
if (!punchFreeze) { /* 이동 전체 */ }      // (3) 적용 단계에서 또 차단
```

**증상이 코드 구조와 정확히 일치했다** — 자동 조준은 `punchFreeze` 블록 *바깥*, 이동은 *안*에
있었고, 사용자 보고도 "회전은 되는데 이동만 안 된다"였다.

고친 방향은 "잠금을 없애기"가 아니라 **무엇을 잠글지 나누기**였다.
잠금의 목적은 *오염된 신호로 새 방향이 생기는 것*을 막는 데 있다. 잠금 직전에 이미 확정돼 있던
이동 의사는 펀치가 만든 것이 아니므로 죽일 이유가 없다. 그 값을 붙잡아 두고 계속 적용한다.

*하니스 실측:* 같은 조건(0.25초 간격 연타, pitch 오염 ±0.30)에서 **옛 로직 0.0 units /
현재 39.4 units**. 동시에 "가만히 선 채 연타하면 밀리지 않는다"도 0.0000으로 유지된다.

### 1-3. 3D 얼굴이 두개골 안쪽에 있었다

얼굴 메쉬를 구(반지름 1.3) 안쪽 `z=0.62`에 배치해 얼굴 대부분이 잠겼다. host든 1인칭이든
보일 리가 없었다. **배치를 상수로 박은 것**이 잘못이다 — 얼굴 깊이는 사람마다 다르다.

이제 정점마다 정확히 역산한다. 두개골 타원체 밖 조건을 각 정점에 대해 `d`로 풀어 최댓값을 취한다.

```
(x/a)² + (y/b)² + ((z+d)/c)² ≥ 1
k = 1 − (x/a)² − (y/b)²      k ≤ 0 이면 x·y 만으로 이미 바깥
그 외에는  d ≥ c·√k − z
```

`bounds.zMin` 하나로 어림하면 안 된다. **가장 뒤쪽 정점이 가장 깊이 박히는 정점이 아니기
때문이다** — 옆으로 벌어진 뺨은 타원체가 좁아지는 자리라 오히려 여유가 있고, 가운데 낮은
정점이 더 위험하다.

### 1-4. host 화면에는 얼굴이 아예 안 떴다

`arena.html`에 `face3d.js`는 넣었는데 **`face_mesh` CDN을 안 넣었다.** 얼굴 토폴로지
(`FACEMESH_TESSELATION`)가 없으니 삼각형을 못 만들고 `createFace3D`가 통째로 실패한다.
"host는 얼굴을 *촬영*하지 않으니 라이브러리가 필요 없다"고 넘겨짚은 것이 원인이다.
`FaceMesh` 인스턴스를 만들지 않으므로 무거운 WASM은 받지 않는다 — 스크립트만 있으면 됐다.

## 2. 두 계층의 하니스

위 네 건 중 **1-3, 1-4는 로직 하니스가 전부 통과시켰다.** THREE 최소 스텁 위에서 순수 로직만
보기 때문에 "페이지가 실제로 그려지는가"는 볼 수 없다. 결정적인 사례가 하나 더 있다.

```
TypeError: fx.update is not a function
    at animate (.../client?id=client_2:1122:10)
```

이펙트 매니저를 `const fx`로 받았는데 `animate()` 안에 **원래부터 정면 벡터 `const fx`**가
있었다. 안쪽이 바깥쪽을 가려 매 프레임 예외가 났고, 그 지점이 `renderer.render()` **직전**이라
3D가 한 번도 안 그려졌다. `requestAnimationFrame`은 함수 맨 위에서 이미 예약되므로 루프는 계속
돌고, 웹캠 캔버스 그리기는 예외 지점보다 앞이라 멀쩡했다 — "웹캠은 되는데 3D만 안 보인다".

그래서 하니스를 두 계층으로 나눴다.

| 계층 | 무엇을 보는가 | 종수 |
|---|---|---|
| 로직 (THREE 스텁) | 알고리즘이 맞는가 | 7 |
| **실제 브라우저 (헤드리스 Chrome + CDP)** | **페이지가 사는가** | 4 |

브라우저 계층은 npm 의존성 없이 Node 22 내장 `fetch`/`WebSocket`만 쓴다. WebGL은
SwiftShader 소프트웨어 렌더링이라 GPU 없는 환경에서도 돈다.

### 2-1. 하니스가 자기 자신의 오류도 잡았다

- **테스트에 로직을 베껴 쓰면 안 된다.** 런타임과 조용히 어긋나 정작 잡아야 할 회귀를 통과시킨다.
  그래서 판정 로직을 `punch_core.js`로 빼 **브라우저와 Node가 같은 모듈을 import** 하게 했다.
- 훅을 **직선 이동**으로 모델링했더니 속도가 과소평가돼 발동조차 안 됐다. 실제 훅은 손목이 호를 그린다.
- 그 호가 **중앙을 가로지르지 않아** 임팩트 순간 속도가 전방이었고 `STRAIGHT`로 분류됐다.
  실제 훅은 바깥에서 들어와 상대를 *지나쳐* 가므로 정면 통과 순간 속도가 순수 횡방향이다.
- 옛 머리 반지름(1.3)을 하드코딩해 얼굴 배치 검사가 틀렸고, 다리 길이를 `hipY/height`로 재
  발이 y=0이라고 가정했다. 이제 상수를 **소스에서 읽는다.**
- 밸런스 검사에서 최강기를 데미지 표 전체의 최댓값으로 잡았더니, **아무도 쓸 수 없는**
  `ENERGY_WAVE`가 최강기가 되어 "6대면 죽는다"는 엉뚱한 실패가 났다.

마지막 항목이 문서 검사를 만든 계기다. README가 반복적으로 코드와 어긋났고 —
데미지 표는 밸런스를 바꾼 뒤에도 옛 값이 남았고, `ENERGY_WAVE`는 **감지 로직이 없어 발동조차
못 하는데** 사용 가능한 기술로 적혀 있었다. **조작 문서가 틀리면 사용자는 "기능이 고장났다"고
판단한다.** 실제로 그런 보고가 여러 번 있었다. `doc_harness.js`가 임계값 26개·데미지 표·
액션 목록·미구현 표기를 코드에서 뽑아 문서와 대조한다.

## 3. CV 파이프라인

### 3-1. 모션 인식 — 손가락에서 상체로

처음에는 MediaPipe Hands(21×2 = 42노드)를 썼다. 손가락 마디로는 몸 전체 모션을 읽을 수 없어
Pose 상체 **7노드**(코·양어깨·양팔꿈치·양손목)로 옮겼다. 추적 노드는 42 → 7로 줄고 인식 대상은
손가락에서 상체 전체로 넓어졌다.

모든 지표는 **어깨폭 단위로 정규화**하고 **중립 자세 대비 편차**로 계산한다. 카메라 거리·체형·
해상도가 달라도 같은 임계값이 통한다.

**펀치는 창(window) 래치로 판정한다.** 신전 구간이 0.15초 안팎이라 여러 조건을 한 프레임에서
동시에 만족하도록 요구하면 *속도가 최고인 프레임은 아직 덜 뻗었고 / 다 뻗은 프레임은 이미 감속*
해서 놓친다. 그래서 조건을 시간 창에 걸쳐 누적한다.

1. 빠르게 뻗기 시작하면 창을 연다 (손목 1.0 m/s ∧ 뻗음 증가율 0.40 m/s)
2. 창(380ms) 동안 **최고 속도와 그 순간의 궤적 방향·팔꿈치 각도**를 기록
3. 충분히 뻗은 시점에 발사 (최고속도 1.6 m/s ∧ 뻗음 0.88배 또는 +0.28배)

분류를 **최고 속도 순간**의 값으로 하는 것이 요점이다. 감속 구간의 방향으로 분류하면 종류가
엉뚱하게 잡힌다.

### 3-2. 단안 3D 얼굴 복원

기존 검토는 세 안을 놓고 저울질했다.

| 안 | 결과물 | 비용 |
|---|---|---|
| A. 사진을 구에 텍스처 | 정면만 맞는 2.5D | 낮음 |
| B. DECA/FLAME 오프라인 복원 | 진짜 3D | Python·GPU·GLB, 시간 리스크 큼 |
| C. 다중 뷰 빌보드 | 중간 | 단순성 대비 이득 작음 |

**네 번째 길이 있었다.** MediaPipe Face Mesh가 브라우저에서 468개 3D 랜드마크를 준다.
고정 토폴로지를 쓰므로 랜드마크를 정점으로, 테셀레이션을 삼각형으로 삼으면
사진 한 장에서 **그 사람의 실제 3D 얼굴 메쉬**가 나온다. **B의 결과물을 A의 비용으로** 얻는다.

그리고 이 선택이 게임에 직접 값을 한다 — 진짜 메쉬라서 "맞으면 일그러지고 HP가 낮으면 표정이
바뀌는" 것을 정점 변형으로 표현할 수 있다. 텍스처를 입힌 구였다면 불가능했다.

FPS는 **Face Mesh를 촬영 순간에만 돌리고 즉시 끄는** 것으로 해결했다(두 모델 동시 실행 시
30fps 이하로 떨어진 이력이 있다). 복원된 메쉬는 정적이라 게임 중 추가 비용은 0이다.

**세 가지 함정이 있었다.**

1. **`FACEMESH_TESSELATION`은 삼각형이 아니라 간선 쌍 목록**이고, 같은 간선을 `[a,b]`와
   `[b,a]`로 **양방향 모두** 담는다(2556개 = 1278 × 2). 3-사이클 탐색으로 삼각형을 복원하면
   이웃이 두 번 들어가 같은 삼각형이 **2×2 = 4번** 잡힌다(3288개).
   실은 이 배열이 삼각형 목록에서 생성된 것이라 **3개씩 묶으면 한 삼각형**이다
   (852개 그룹 전부가 닫힌 삼각형, 어긋난 그룹 0개). 추측할 이유가 없었다.
2. **비등방 정규화** — MediaPipe 좌표는 x를 이미지 *폭*으로, y를 *높이*로 각각 나눈 값이다.
   480×360에서 그대로 쓰면 x가 0.75배로 눌려 **얼굴이 세로로 길쭉해진다.**
3. **MediaPipe가 결과 캔버스를 재사용한다.** `res.image` 참조만 붙잡아 두면 캡처가 끝날 때쯤
   다른 프레임 그림으로 덮여 있다. 텍스처는 A 프레임인데 랜드마크는 12프레임 평균이라
   눈·입이 밀린 "남의 얼굴"이 나온다. 형태는 평균이 맞지만(지터 제거) **UV는 텍스처를 딴 바로
   그 프레임의 좌표**여야 한다 — 둘을 분리했다.

### 3-3. "가면"의 정체

얼굴 메쉬만 씌우면 **두개골은 원래 색 그대로**라 얼굴 가장자리에서 색이 뚝 끊긴다.
그 경계선이 "얼굴을 붙인 머리"가 아니라 "가면을 쓴 인형"으로 보이게 만든다.

얼굴 텍스처에서 **평균 피부톤을 뽑아**(볼·코 주변만 표본, 그림자·하이라이트 픽셀 제외)
머리·목·팔다리를 같은 톤으로 맞추니 경계가 사라졌다.

## 4. 사람마다 다른 몸

전진/후진 임계값을 세 번 고쳤다.

| 차수 | 전진 발동 | 후진 발동 | 근거 |
|---|---:|---:|---|
| 4차 | 0.16 | 0.12 | "사람은 뒤로 조금밖에 못 젖힌다" |
| 12차 | **0.105** | **0.175** | 실사용은 정반대였다 |
| 16차 | 사람마다 측정 | 사람마다 측정 | 고정값으로는 아무에게도 안 맞는다 |

12차에서 뒤집은 이유는 신호 구조에 있었다. 전진 신호는 얼굴·주먹·어깨폭 여러 항으로 **분산**되는
반면, 후진은 얼굴이 올라가는 **한 가지 신호**로 곧장 잡힌다. 같은 임계값이면 후진만 과하게 걸린다.

그런데 뒤집었더니 이번엔 반대쪽이 안 맞았다. **기울일 수 있는 범위가 사람마다·카메라 각도마다
크게 다르다**는 것이 진짜 원인이었다. 중립 자세는 이미 보정하고 있었지만 *범위*는 보정하지
않고 있었다. 3단계 마법사(중립 → 최대 전진 → 최대 후진)로 재고, 측정한 최대 기울기의 **45%**를
발동 임계로 잡는다. `localStorage`에 저장해 다음 접속에도 유지된다.

## 5. 게임 규칙에서 배운 것

**분노 게이지** — 맞을수록 찬다(데미지 1당 2.2, 7~9대면 가득). 지고 있는 쪽에 역전 수단을 주어
경기가 끝까지 팽팽하도록 한 장치다. 가득 차면 몸에서 불꽃 오라가 일고 필살기를 쓸 수 있다.

여기서 실측으로 버그를 하나 잡았다. 처음엔 가득 찬 게이지도 감쇠시켰더니 100에 닿는 순간부터
곧바로 깎여 **99.1에서 맴돌았다.** 사용 조건이 "가득 참"이라 필살기를 **영영 못 쓴다.**
1절의 조용한 실패와 같은 형태다 — 예외도 없고, 게이지는 꽉 차 보인다.

**데미지 밸런스** — 초기값(잽 12 / 어퍼 25)은 속도 보너스까지 받으면 3대면 죽었다.
"최소 10대는 버틴다"를 만족하도록 역산해 잽 5 / 어퍼 8, 속도 보너스 상한 +25%로 잡았다.
실측으로 크로스 17대 / 어퍼컷 10대다.

## 6. 실영상으로 채점해 보니

하니스 272개가 전부 통과한다. 그런데 하니스는 **로직이 내가 의도한 대로 도는가**만 본다.
합성 궤적을 넣으면 합성 궤적에 맞춰 만든 임계값이 당연히 맞는다. "실제 사람이 잽을 뻗었을 때
잽으로 잡히는가"는 여기서 알 수 없다.

그래서 90초짜리 영상을 찍고 구간별 정답 라벨을 붙였다 — 준비 / 직선 / 훅 / 어퍼컷 / 풋워크 /
콤보 / 마무리, 사이사이에 숨고르기. **동작 구간과 비동작 구간을 명시적으로 나눈 것**이 핵심이다.
"몇 개 맞혔나"만 세면 헛발사를 놓친다.

### 결과

| 지표 | 값 |
|---|---:|
| 정답 / 검출 | 29 / **59** |
| TP / FP / FN | 17 / 42 / 12 |
| 정밀도 | **0.288** |
| 재현율 | 0.586 |
| F1 | 0.386 |
| 기술 종류 정확도 | 0.235 |
| 좌우 정확도 | 0.471 |
| 타이밍 오차 | 평균 111.9 ms / 최대 300 ms |

재현율 0.586은 나쁘지 않다. 문제는 **29개를 맞히려고 59개를 쏜다**는 것이다.

| 구간 | 성격 | 검출 |
|---|---|---:|
| 1. 준비 00~06s | 비동작 | 0 |
| 2. 직선 06~18s | 동작 | 5 |
| 3. 훅 23~35s | 동작 | **17** |
| 4. 어퍼컷 40~52s | 동작 | **15** |
| **5. 풋워크 57~70s** | **비동작** | **9** |
| 6. 콤보 75~85s | 동작 | 11 |
| 숨고르기 4구간 | 비동작 | 2 |

두 가지가 보인다.

**첫째, 풋워크에서 9번 헛나간다.** 스텝을 밟으면 상체가 좌우로 흔들린다. 판정은 손목 속도를
**어깨 기준으로** 재는데, 어깨 자체가 움직이면 가만히 있는 손도 빠르게 움직인 것으로 읽힌다.
어깨폭으로 정규화한 것은 사람마다 다른 체격을 흡수하려는 것이었지 몸통 흔들림을 빼려는 게
아니었다. 몸통 자체의 속도를 빼는 보정이 없다.

**둘째, 훅·어퍼 구간이 정답보다 훨씬 많다.** 한 번 뻗을 때 여러 번 발사되는 것으로 보인다.
쿨다운(같은 팔 400ms / 아무 팔 200ms)이 있는데도 이렇다는 것은, 훅처럼 궤적이 긴 동작이
쿨다운을 넘겨 계속 조건을 만족시킨다는 뜻이다.

기술 종류 정확도 0.235는 사실상 찍는 수준이다. 맞힌 17개 중에서도 STRAIGHT를 HOOK·UPPERCUT·
CROSS로 흩어 놓는다.

### 게임에서는 왜 몰랐나

플레이할 때 체감은 나쁘지 않았다. 이유가 있다 — **과검출은 "잘 나간다"로 느껴진다.**
주먹을 뻗었는데 두 번 나가면 손해 보는 기분이 안 든다. 헛발사도 상대에게 맞지 않으면
그냥 허공을 친 것으로 보인다. 즉 **체감으로는 정밀도를 절대 못 잡는다.**
라벨을 붙인 영상이 필요했던 이유다.

### 그리고, 평가기가 판정 코드를 읽지 않고 있었다

판정 튜닝을 여러 차례 바꾼 뒤 이 파이프라인을 돌려 이전 결과와 비교했다.
**한 수치도 안 바뀌었다.** 절대경로 한 줄을 빼면 결과 파일이 비트 단위로 동일했다.

```
- "source_video": "C:/hong/project-4/..."
+ "source_video": "C:/두루미/project-4/..."
```

평가기가 `punch_core.js` 를 읽는 대신 **상수를 자기 파일에 복사해** 갖고 있었다.
런타임을 어떻게 고치든 점수는 안 움직인다.

값을 하나씩 대조했다. 펀치 상수 12개는 마침 일치했다 — 그래서 위 점수는 유효하다.
그런데 같은 폴더의 전체동작 평가기는 어긋나 있었다.

| | 평가기 | 런타임 |
|---|---:|---:|
| PITCH_ON | 0.16 | **0.105** |
| PITCH_BACK_ON | 0.12 | **0.175** |
| SHIFT_ON | 0.22 | **0.40** |
| (외 9개) | | |

게다가 필살기 상수가 아예 없어 **필살기 판정이 통째로 빠져 있었다.** 다행히 현재
이 파일을 호출하는 곳이 없어 점수를 오염시키진 않는다.

이것이 1절의 조용한 실패와 정확히 같은 형태라는 점이 중요하다. **평가기는 에러 없이 잘 돌고,
숫자를 내놓고, 그 숫자가 틀렸다는 신호를 아무것도 주지 않는다.** 측정 도구가 조용히 어긋나면
그 위에 쌓은 모든 판단이 어긋난다.

근본 해법은 평가기가 Node로 `punch_core.js` 를 직접 실행하는 것이다. 판정 로직을 HTML에서
독립 파일로 분리하면서 **DOM·THREE·MediaPipe 의존을 0으로** 만든 것이 이걸 위해서였다 —
브라우저는 `<script>` 로, Node는 `require` 로 같은 파일을 읽을 수 있다. 남은 것은 평가기의
실행자만 갈아끼우는 일이고, 그때도 라벨·랜드마크 캐시·채점기는 그대로 재사용된다.

### 부수적으로 고친 것

파이프라인이 시작조차 안 됐다 — `ModuleNotFoundError: No module named 'cv2'`.
그런데 랜드마크 추출 단계는 **캐시가 있으면 통째로 건너뛴다.** 실제로 캐시가 이미 있었다.
즉 영상 디코딩이 한 번도 필요 없는데 최상단 import 때문에 막힌 것이다.
(mediapipe는 Python 3.13 휠이 아직 없어서 앞으로도 계속 걸릴 자리다.)

`cv2`/`mediapipe` 를 영상 경로에서만 지연 로딩하도록 바꿨다. 판정 로직은 한 줄도 안 건드렸고,
**점수가 동일하다는 것이 그 증거다.**
