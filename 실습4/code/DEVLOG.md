## 2026-08-26 (수) — [iter3] 19차: 동작 인식 rule-base → 학습 모델(TCN) 전환, UI에서 엔진 선택

### 배경

`motion_learning/collected_pose`에 4명(cheols·hong·kim·suhwan) × 10라벨 × 5회 = 200개의
실측 포즈 샘플이 있었지만, 학습 스크립트(`train_gpu_motion.py`)는 실제로는 이 데이터를 쓰지
않고 synthetic 데이터로만 학습하고 있었다. 게임의 펀치 인식(`punch_core.js`)도 순수
rule-base(손목 속도벡터 방향 + 팔꿈치 각도 임계값)였다.

### 한 일

1. **outlier 제거** (`outlier_filter.py`) — 라벨과 실제 동작이 어긋난 샘플을 클래스 내부
   robust z-score(median/MAD)로 탐지, 200개 중 17개 제외 (`outlier_report.json`).
2. **causal TCN 학습** (`tcn_model.py`, `train_tcn_real.py`) — 참가자 단위 LOSO 교차검증으로
   rule-base와 정면 비교. 첫 시도(관절 절대좌표 70차원)는 참가자별 카메라 거리가 사람 지문으로
   학습돼 rule-base보다 낮게 나왔고, 상대값뿐인 `heuristic_7j_v1`(17차원)로 바꿔 해결.
   **결과: rule-base 33.3% → TCN 49.2% 정확도(LOSO), macro-F1 0.29 → 0.49**
   (`eval_results_real.json`). 특히 rule-base가 아예 못 잡는 `TWO_HAND_GUARD`(F1 0.48→0.74)에서
   격차가 크다. (ENERGY_WAVE 비교는 이 LOSO 실험 당시엔 rule-base에 그 개념 자체가 없어 F1이
   0으로 나왔는데, 이후 별도로 `tryUltimate` 트리거가 rule-base에도 생겨 이 비교는 지금은 낡았다 —
   아래 "병합" 절 참고.)
3. **실시간 통합** — `boxing_tcn.onnx` + `boxing_tcn_scaler.json`을 `server/static/models/`에 배치,
   `motion_features.js`(브라우저에서 heuristic_7j_v1 근사 피처 추출)와 `tcn_engine.js`
   (onnxruntime-web 추론)를 신설. `fighter_client.html`의 `action-hud`에 **Rule-base / TCN
   드롭다운**을 추가해 플레이어가 실시간으로 전환 가능(선택은 `localStorage`에 저장).

### 설계 결정 — 무엇을 바꾸고 무엇을 안 바꿨나

- **펀치가 나가는지·언제·어느 팔인지(트리거)와 이동·회전·가드는 모드와 무관하게 항상
  rule-base(`punchCore.tryPunch` + 자세 로직) 하나만 담당한다.** 두 모드가 갈리는 지점은
  딱 하나, **"이미 확정된 일반 펀치의 종류를 무엇으로 판단하는가"** 뿐이다. (아래 실측 피드백
  두 건 모두 이 원칙을 어겼던 것이 원인이었다 — 처음엔 TCN이 트리거까지 가져갔었다.)
- **라벨 표기 불일치**: 수집 데이터·모델은 오른손 스트레이트를 `RIGHT_JAB`으로 부르지만
  게임 전역(app.py/humanoid.js/arena.html)은 `RIGHT_CROSS`로 부른다. `tcn_engine.js`가
  게임에 내보내는 순간에만 변환한다(`ACTION_ALIAS`).
- 실시간 속도·가속도 피처는 원본 수집 파이프라인(이 저장소엔 소스가 없음)의 정확한 평활 방식을
  못 찾아 backward-difference로 근사했다 — 각도·거리·비율 9개 채널은 실측 데이터와 소수점까지
  일치를 확인했지만, 속도 8개 채널은 스케일만 맞춘 근사치다. 실제 웹캠 스모크 테스트로
  재확인 필요(이 세션엔 브라우저·웹캠이 없어 못 함).

### [실측] TCN 모드 오검출 다발 — `tryFire` 레벨 트리거 버그 → 이후 아키텍처 재수정

실제로 TCN 모드로 플레이해보니 가만히 있어도 원치 않는 펀치가 계속 나갔다. 1차 진단: `tryFire()`가
발동 시 `confirmSince`만 초기화하고 `confirmLabel`은 그대로 둬서, 모델이 같은 라벨을 계속
유지 예측하면 쿨다운 주기마다 무한 재발동했다(엣지가 아니라 레벨로 판정한 버그). 디바운스를
고쳤는데도 여전히 오검출이 잦다는 후속 피드백을 받고 다시 보니, 애초 설계 자체가 틀려 있었다:
`tcn_engine.js`가 "펀치 종류"뿐 아니라 "펀치가 지금 나가는지(trigger)"까지 자체 디바운스로
결정하고 있었던 것 — `punchCore.tryPunch`는 실제 속도·뻗음이 물리 임계값을 넘어야만 창이
열리는데, TCN 자체 트리거는 그냥 "분류기가 그 순간 뭐라고 보는가"였으므로 노이즈에 훨씬 약했다.

**최종 수정**: `tcn_engine.js`에서 발동(`tryFire`) 개념을 완전히 제거했다. 이제 어느 모드든
펀치 트리거는 `punchCore.tryPunch` 하나만 결정하고, TCN은 `guessPunchKind(side)`라는
1회성 조회 함수만 제공한다 — rule-base가 이미 확정한 펀치에 대해 "그 순간 모델이 충분한
확신으로 같은 팔의 펀치 라벨을 보고 있는가"만 답하고, 아니면 null을 돌려줘 rule-base의
`classify()` 결과가 그대로 쓰이게 한다. HUD 표시용 `stableState()`는 200ms 유지돼야 반영되는
별도 디바운스 값으로 분리해 판정 로직과 완전히 독립시켰다.

### [병합] origin/iter3 6개 커밋과 합치며 — 필살기가 이미 rule-base로 해결돼 있었다

이 파일을 작업하는 동안 원격에 `punch_core.js`(75줄) · `humanoid.js`(514줄) · `app.py`(171줄)를
건드리는 커밋 6개가 쌓여 있었다. 로컬 미커밋 변경분(순수 TCN 관련, 72줄 추가/2줄 삭제였음을
`git diff`로 먼저 확인)을 패치로 백업해두고, `fighter_client.html`·`DEVLOG.md`는 원격 버전으로
되돌린 뒤 fast-forward pull, 그 다음 TCN 훅만 새 코드 위치에 다시 얹었다 — "다른 부분은 기존
코드"를 지키기 위해 자동 3-way 머지에 맡기지 않고 수동으로 재적용했다.

가장 중요한 변화: 위에서 "ENERGY_WAVE는 `tryPunch`가 팔 하나짜리 펀치만 감지해서 트리거할 수
없다"고 적었던 제약이 **원격 쪽에서 독립적으로 해결돼 있었다** (`필살기 동작 교체` 커밋).
`punchCore`에 `tryUltimate`/`isUltArmed`/`ultCharge`가 새로 생겼고, "양손을 머리 위로 들고
0.35초 유지"라는 속도-무관 정적 자세로 필살기를 트리거한다. 이 구조에서도 원칙은 그대로 지킨다:
필살기는 "펀치 종류"가 아니라 별도 제스처이므로 TCN은 여기 전혀 관여하지 않는다 — 트리거·종류
모두 `punchCore.tryUltimate`가 정하고, TCN의 `guessPunchKind`는 `punch.action !== punchCore.ULTIMATE`일
때만 호출한다.

## 2026-08-27 (목) — [iter3] 18차: 벤치마크 재실행 · 평가기 의존성 분리

### [18:40] 팀원 평가 파이프라인을 현재 코드로 돌렸다

`eval/` 파이프라인이 병합되어 들어왔다. 내가 12~17차에서 판정 튜닝을 여러 번 바꿨으므로
점수가 어떻게 움직였는지 확인했다.

**결론: 한 수치도 안 바뀌었다.** 절대경로 한 줄을 빼면 `runs/v1_baseline/metrics.json` 이
비트 단위로 동일하다.

```
- "source_video": "C:/hong/project-4/..."
+ "source_video": "C:/두루미/project-4/..."
```

당연한 결과다. **평가기는 `punch_core.js` 를 읽지 않는다.** 상수를 자기 파일에 복사해 갖고
있으므로 런타임을 어떻게 고치든 이 숫자는 안 움직인다. 그래서 값을 직접 대조했다 —
`evaluate_video.py` 의 펀치 상수 12개는 현재 `punch_core.js` 와 **전부 일치**한다.
우연이 아니라 맞춰 둔 것이고, 따라서 이 점수는 현재 런타임 펀치 판정의 실제 성능이 맞다.

다만 같은 폴더의 `evaluate_full_actions.py` 는 어긋나 있다.

### [15:10] 필살기 — 속도를 요구하지 않는 정적 자세로

- **증상**: "양손 모았다가 앞으로 하라는데 인식이 잘 안 된다."
- **원인**: 밀어내는 **순간의 속도와 뻗음을 동시에** 요구했다. 자세가 조금만 어긋나거나
  미는 속도가 모자라면 그대로 놓친다. 펀치는 창(window)으로 시간에 걸쳐 누적하는데
  필살기에는 그런 장치가 없었다.
- 손가락 랜드마크를 쓰면 정교하겠지만 Pose+Hands 병용이라 FPS 가 무너진다.
- **교체**: **양손을 머리 위로 들고 0.35초 유지.** 속도를 아예 안 본다.

| 조건 | 값 | 무엇과 구분되는가 |
|---|---|---|
| 손목이 코보다 위 | 어깨폭 0.28배 | 가드는 턱 높이가 최대 — 복싱 중 안 나오는 자세 |
| 양손 모두 | — | 한 손 펀치·훅 |

### [15:10] 얼굴 — 뒤통수를 만들어 붙인다

- **증상**: "여전히 아바타에 가면 쓴 것처럼 보인다. 앞·옆·뒤 전부 사람처럼."
- 15~16차에서 피부톤을 맞추고 두개골 구를 남겼지만, 결국 **판(얼굴) + 공(구)** 두 덩어리라
  경계가 남는다. 옆에서 보면 얼굴이 공에 붙은 판으로 보인다.
- **해결**: `FACEMESH_FACE_OVAL`(36점 닫힌 루프)이 "얼굴이 끝나는 선"이다.
  이 테두리를 적도로 보고 **뒤쪽 극점까지 위도를 나눠 링을 쌓아 두개골을 생성**한다.
  테두리에서 출발하므로 이음매가 정확히 맞고, 사람마다 다른 얼굴 윤곽을 그대로 따라간다.

|---|---:|
| 얼굴 삼각형 | 852 |
| **두개골 포함** | **1392** |

1. **훅을 직선 이동으로 모델링했다** — 실제 훅은 손목이 **호를 그리며** 돌아서

하니스의 값어치를 좌우한다.

```js
if (locked) {
  moveState = lockedMove.state;                                  // 새 상태는 안 생김
  lockedMove.intensity *= Math.exp(-dtPose / TUNE.PUNCH_MOVE_DECAY);  // 계속 치기만 하면 서서히 멎음
  moveIntensity = lockedMove.intensity;
  rotState = "NONE"; rotIntensity -> 0;                          // 회전은 계속 완전 차단
  return;
}
```

- 회전만 여전히 완전 차단한다. **주먹 좌우 이동이 곧 회전 신호**라 펀치와 정면으로 겹친다.
  이동(얼굴·어깨 기울기)은 겹치지 않으므로 같이 막을 이유가 없었다.
- `PUNCH_LOCK` **480 → 180ms**. 480ms는 팔이 오염을 일으키는 구간보다 훨씬 길었다.
  실제 보호는 `PUNCH_LOCK_MAX`(1100ms) + `armsBusy`(팔이 아직 나가 있는지)가 담당하므로,
  하한은 "팔이 확실히 나가 있는 최소 시간"만 덮으면 된다.
- `animate`의 `punchFreeze` 이동 차단 제거 — 잠금 처리를 `updateStates` 한 곳으로 일원화했다.
  `moveIntensity`가 이미 잠금을 반영하므로 그대로 적용하면 된다.
- **자동 접근(engage pull)은 잠금 중에도 돌린다.** 타깃 방향만 보므로 자세 오염과 무관하다.
- 잠금 시 early return 하게 되어 뒤따르던 `!locked` 가드 4개는 죽은 코드가 되어 정리했다.

## 2026-08-25 (화) — [iter3] 4차 평가 피드백: 전진 모션이 발동하지 않음

### [19:20] 원인 — 대칭 항을 통째로 빼버린 것이 과했음

- **경위**: 후진을 고치면서 `bodyDrop`(상체가 화면에서 내려간 정도)이 **방향에 대칭**이라는 이유로

- **남은 어깨폭 항의 한계**: 카메라에서 조금 떨어져 서 있으면, 앞으로 숙여도 겉보기 어깨폭이 거의 안 바뀐다.
  게다가 몸통이 조금만 틀어져도 투영 폭이 줄어 상쇄된다. 그 결과 전진 점수가 임계값에 못 닿았다.
- 실제로 "제자리에서 숙이되 카메라에는 거의 안 다가가는" 자세(어깨폭 +2%)를 넣어보면
  `0.45·0.20 + 0.25·0.15 + 1.4·0.02 = 0.156` — 임계값 0.18 미달. 하니스로 재현 확인.

### [19:20] 수정 — 대칭 항을 "방향 결정"이 아니라 "증폭"에만 쓴다

두 항의 성질이 다르다는 점을 구조로 반영했다.

```
dirTerm   = 0.45·얼굴 + 0.25·주먹 + 1.20·어깨폭증가율     ← 반대칭. 방향을 결정한다
bodyBoost = conf · 0.30 · max(0, 상체하강)                ← 대칭. 방향은 못 정하므로 키우기만 한다
pitch     = dirTerm + bodyBoost
conf      = clamp01(dirTerm / 0.08)   // 부호 경계에서 튀지 않게 부드럽게 켜짐
```

- **전진**: `dirTerm > 0`이므로 `bodyBoost`가 온전히 실린다 → 예전처럼 주력 신호로 동작
- **후진**: `dirTerm < 0`이면 `conf = 0` → `bodyBoost`가 **아예 0**. 더 이상 후진을 상쇄하지 않는다
- 대칭 항을 빼지도, 그대로 더하지도 않고 **부호가 이미 정해진 뒤에만 기여**하게 한 것이 요점이다.
- 전진 임계값도 `0.18 → 0.16`으로 소폭 완화.

**효과 (하니스 실측)**

| 자세 | face | fist | body | near | 합계 | 판정 |
|---|---|---|---|---|---|---|
| 얕은 전진(카메라 접근 거의 없음) | +0.09 | +0.04 | **+0.07** | +0.02 | **+0.22** | FORWARD (임계 +0.16) |
| 후진 | −0.06 | −0.04 | **0.00** | −0.07 | **−0.16** | BACK (임계 −0.12) |

### [16:40] 펀치 인식 실패 원인 규명 및 수정

평가 피드백: **펀치가 잘 인식되지 않음**. 원인을 4가지로 분리해 각각 대응했다.

**(1) [핵심] 판정 3조건이 같은 프레임에 겹쳐야 했던 구조**

기존 `tryPunch()`는 `속도 > 2.0` ∧ `뻗음속도 > 0.7` ∧ `뻗음 > 0.38m`을 **한 프레임에서 동시에**
만족해야 발동했다. 그런데 펀치 신전 구간은 0.15초 안팎이라 15fps에서는 2~3 샘플뿐이고,
**속도가 최고인 프레임은 아직 덜 뻗었고 / 다 뻗은 프레임은 이미 감속**해서 양쪽 다 탈락하는
구간이 생긴다. 이것이 주된 실패 모드였다.

→ **창(window) 래치 방식**으로 교체:
1. 팔이 빠르게 뻗기 시작하면(`속도 > 1.2 m/s` ∧ `뻗음속도 > 0.45 m/s`) 창을 연다
2. 창(320ms) 동안 **최고 속도와 그 순간의 궤적 방향**을 누적 기록한다
3. 팔이 충분히 뻗은 시점(`뻗음 > 어깨폭 0.95배` **또는** 창 시작 대비 `+0.30배` 증가)에 발사한다

종류 분류도 현재 프레임이 아니라 **최고 속도 순간의 속도 벡터**로 수행하므로,
감속 구간에서 엉뚱하게 분류되지 않는다. 회귀 테스트를 하니스에 추가했다
(`punch split across frames still fires` — 기존 로직으로는 반드시 실패하는 케이스).

**(2) 가드가 펀치를 막고 있었음**

`!guardActive` 조건 때문에 가드 판정 중에는 펀치가 아예 발동하지 않았다.
그런데 **제대로 된 복싱 스탠스는 항상 두 주먹이 얼굴 옆에 있어서 가드 조건을 상시 만족**한다.
자세를 잘 잡을수록 펀치가 안 나가는 역설. → 조건 제거.
가드 중인 팔은 애초에 빠르지도 뻗지도 않으므로 운동학 조건만으로 충분히 걸러진다.

**(3) 양팔 visibility를 AND로 묶어 단일 실패점이 됨**

기존 `wristOK`는 **좌우 팔꿈치·손목 4개 전부** `visibility ≥ 0.5`를 요구했다.
넷 중 하나만 흔들려도 펀치 판정 전체가 정지한다. 빠르게 움직이는 팔은 visibility가 잘 떨어지고,
정면으로 뻗으면 팔꿈치가 손에 가려 자기 가림(self-occlusion)이 생긴다.
→ **팔별로 독립 판정**(`armVis.L` / `armVis.R`)하고, 펀치용 하한을 `ARM_VIS_MIN = 0.3`으로 분리.

**(4) 시간 해상도 부족**

`modelComplexity: 1` + 66ms 스로틀(~15fps)에서는 펀치가 2~3 샘플에 불과했다.

- **오검출 억제**: 신호 EMA(α=0.35) → 임계값 히스테리시스 → **연속 3프레임 투표**(해제는 2프레임)

- 영향: `server/app.py` `process_attack()`

- **서버 로그**: 공격 패킷 수신 시 `[RECV]`, 각 타겟별 거리/각도/OK/MISS `[ATK]`, 실제 HIT `[HIT]` 로그 출력. 쿨다운 차단도 `[ATK] BLOCKED` 로그.

### [21:30] Arena 아바타 이동 버그 원인 발견 — client_id 오타 방어
- **원인**: 사용자가 URL에 `client?id=clinet_1` (오타)로 접속 → 서버의 `fighters` dict에 없는 키 → arena에서 `fighterMeshes["clinet_1"]` 미존재 → 패킷 무시 → 아바타 부동.

- 영향: `arena.html`

### [20:30] fighter_client.html 전면 재작성 (FPS + 이동 버그 근본 해결)
- **근본 원인 3가지 해결**:
  1. **FPS 30 문제**: 두 개의 `requestAnimationFrame` 루프 (drawCamCanvas + animate)가 프레임을 분할 → **단일 rAF 루프로 통합**. 캔버스 드로잉은 50ms throttle (20fps).
  2. **주먹만 이동, 본체 고정**: MediaPipe Pose가 실패 시 `poseDetected=true` 고정 → Hands lean 폴백 비활성화 → `leanX/Y=0` → 이동 없음. → **Pose 완전 제거**, Hands 손목 중점 lean만 사용하여 항상 이동 가능.
  3. **앞/뒤 기울임 반전**: MediaPipe 좌표계에서 앞으로 숙이면 cy 증가 → leanY 부호 반전 필요. → `leanY = (cy - neutralY)` 로 수정.
- **기타 변경**:
  - WASD 키 제거, **화살표 키만** 유지 (`e.code` 기반: `ArrowUp/Down/Left/Right`)
  - MediaPipe Hands 주기: 50ms(20fps) → **80ms(~12fps)** — GPU 부하 감소
  - 글러브 SphereGeometry segments: 16 → **12** — 렌더 부하 감소
  - 디버그 HUD: lean 값, calibration 상태, hands 감지 개수, neutral 값, 실제 moveXZ, rotation 모두 표시
- 영향: `fighter_client.html` (전면 재작성)

### [19:00] 서버 성능 최적화 (app.py)
- **`enforce_collision()` 쓰로틀링**: 매 WebSocket 메시지(40+/sec)마다 실행하던 충돌 체크를 `time.monotonic()` 기반 **50ms 간격**(초당 20회)으로 제한. `enforce_collision_throttled()` 메서드 추가.
- **불필요한 broadcast 스킵**: 위치(world_x/z/yaw를 round(2)로 비교)가 변경되지 않은 IDLE 패킷은 broadcast 하지 않음. 공격 패킷, hit 결과, collision correction은 무조건 broadcast.
- **서버 초기 yaw 값 수정**: 클라이언트 `fighterStartConfigs`의 yaw와 일치하도록 수정 (`client_1: -1.5708` 등).
- 영향: `server/app.py`

### [18:30] Arena 뷰 FPS 개선 (arena.html)
- **`playWhoosh()` AudioBuffer 캐시**: 매 호출마다 `createBuffer()`로 새 AudioBuffer를 생성하던 것을 `whooshBuffer` 변수에 캐시하여 재사용 (fighter_client과 동일 패턴). GC 부하 감소.
- **Camera shake 드리프트 방지**: `controls.target`에 랜덤 변위를 누적하던 것을 `shakeDuration === 0` 시 `controls.target.set(0, 0, 0)`으로 원점 복귀. 장시간 플레이 시 카메라 중심점 드리프트 해소.
- 영향: `arena.html`

## 📌 얼굴 사진 → 3D 머리 대체 — 타당성 검토 (2026-08-24)

**결론: 가능하지만 "실시간 브라우저"와 "5일" 제약 안에서 3단계 접근을 권장.**

### 요구사항 정리
- 선수 얼굴 사진 몇 장 → 3D 머리로 렌더링 → 아레나/클라이언트 아바타 머리 교체
- 목표: "얼굴이 진짜 그 사람처럼 보이는 3D"

### 옵션 A — 사진을 텍스처로 입힌 구형/박스 머리 (1~2시간, 저난이도) ★추천
- 얼굴 사진을 `THREE.TextureLoader`로 로드해 머리 구(sphere) 또는 직육면체의 **정면 텍스처**로 매핑.
- 현재 `humanoid.js`의 `head`(구)만 텍스처 입힌 구로 교체하면 됨.
- **장점**: 브라우저에서 즉시 동작, 무설치, 5일 안에 확실히 완료.
- **단점**: 정면만 정확하고 측면/뒤가 왜곡됨(2.5D 수준). 완전한 3D 얼굴은 아님.

### 옵션 B — 사진 → FLAME/DECA 3D 얼굴 재구성 → GLB로 내보내기 (1~2일, 고난이도)
- 오프라인 Python에서 DECA(또는 MICA/FLAME)로 단일/다중 사진 → 3D 얼굴 메쉬 + 텍스처 + 표정/립싱 파라미터 복원.
- 결과를 `.glb`로 export → `THREE.GLTFLoader`로 로드해 humanoid `head` 대체.
- **장점**: 진짜 3D 얼굴, CV 과제(단안 3D 복원)로서 **Show Numbers/창의성** 어필 가능. 회전/측면도 자연스러움.
- **단점**: GPU/Python 환경 필요, 사진 정합·조명 보정·GLB 크기 최적화로 시간 리스크 큼. 삼성 사내 적용 시 FLAME 계열 라이선스(MIT/연구용 혼재) 확인 필요.

### 옵션 C — 정면/측면 사진 → 사진 기반 빌보드 + 머리 매핑 하이브리드
- 정면/후면/측면 사진을 받아 머리에 다중 뷰 텍스처 매핑하거나, 카메라를 마주보는 스프라이트 면.
- A보다 낫지만 B보다 못한 중간. 단순성 대비 이득이 크지 않음.

### 권장
- **이번 발표용은 옵션 A로 즉시 확보**하고, 시간이 남으면 옵션 B(DECA 단안 3D 복원)를 **"차별화 포인트 + Show Numbers"**로 추가.
- 옵션 A 구현 포인트: `humanoid.js`에 `setHeadTexture(url)` API 추가 → `TextureLoader`로 구 머리 `MeshStandardMaterial.map` 설정 → 서버 `static/faces/`에 사진 배치.
- 사진 저작권/초상권: 팀원 얼굴은 본인 동의 확보, 외부 인물은 사용 금지.
