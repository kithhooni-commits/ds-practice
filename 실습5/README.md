# 실습5 — 비전 드럼 연습기

**Computer Vision Practicum** (SNU Visual Computing Lab, 지도: 조한별 / Samsung Electronics DS,
2026-08-24 ~ 08-28). 기존 오픈소스 도구를 조합해 5일 안에 "의미 있고 재미있는" 비전 앱을 만드는 팀 실습.

**웹에서 보기 →** https://kithhooni-commits.github.io/ds-practice/실습5/

## 문제

집에 드럼 세트를 두면 시끄럽고, 비싸고, 자리도 많이 차지한다. 그래서 실제 드럼 대신 웹캠으로 양손
움직임만 추적해 가상 패드를 때리는 연습기를 만든다 — 스피커 볼륨만 줄이면 사실상 무음, 장비값 0원,
바닥 공간 0.

## IN → OUT

```
웹캠 양손 위치·속도 시퀀스  →  패드 히트(합성 드럼음) + 메트로놈 대비 박자 오차(ms)
```

## 아이디어

MediaPipe **Hand Landmarker**(브라우저, `numHands: 2`)로 양손 21개 랜드마크만 가져다 쓰고, 나머지는
전부 직접 짠 로직이다.

- **타격 감지**: 손끝(검지 끝, landmark 8)의 y좌표 변화율(속도)을 매 프레임 계산해, 속도가 감도
  임계값을 아래→위로 "막 넘는 순간"(rising edge)을 타격으로 판정한다. 계속 빠르게 움직여도 같은
  타격을 여러 번 세지 않고, 손을 다시 들어 올렸다가 내려와야 다음 타격으로 잡힌다.
- **패드 6개**: 화면을 2행 3열로 나눠 하이햇·톰1·크래시(위) / 킥·스네어·톰2(아래)를 배치했다. 타격
  순간 손끝이 어느 패드 사각형 안에 있었는지로 어떤 소리를 낼지 정한다. 행 사이 중앙 띠는 "중립
  구간"이라 여기선 히트가 안 나— 실제 스틱을 되돌리는 동작과 비슷하게 설계했다.
- **소리**: 오디오 파일을 전혀 안 쓴다. Web Audio API로 킥(피치가 떨어지는 사인파)·스네어(노이즈
  버스트 + 삼각파)·하이햇(고역 통과 노이즈)·크래시(긴 고역 노이즈)·톰(중저역 사인파)을 그 자리에서
  합성한다.
- **메트로놈**: BPM을 정하고 시작하면, Web Audio의 lookahead 스케줄러로 클릭음을 재생하면서 각 박의
  정확한 오디오 시각을 계산해 둔다. 타격이 들어오면 그 순간과 가장 가까운 박 사이의 시간차(ms)를
  구해 "몇 ms 빠르거나 늦었는지" 로그에 남긴다.

## 구조

| 경로 | 내용 |
|---|---|
| `index.html` | 앱 전체 (HTML/CSS/JS 단일 파일, 서버·오디오 파일 불필요) |

## 사용 기술

- **랜드마크 추출**: `@mediapipe/tasks-vision` `HandLandmarker` (CDN, Apache-2.0), 브라우저에서 WASM 실행, 두 손 동시 추적
- **타격 판정**: 손끝 y속도 기반 rising-edge 검출 + 쿨다운(150ms) + 손이 화면에서 사라졌다 돌아올 때 상태 리셋(200ms)
- **소리 합성 · 메트로놈**: Web Audio API (`OscillatorNode`, `BufferSource` 노이즈, `BiquadFilter`, lookahead 스케줄러)

## 실행 방법

1. `index.html`을 HTTPS 또는 `localhost`에서 연다 (GitHub Pages 링크, 또는 로컬에서
   `python -m http.server`). `file://`로 직접 열면 카메라 권한이 막힐 수 있다.
2. "카메라 + 모델 시작" 클릭 → 카메라 권한 허용 → 모델 다운로드 대기(최초 1회, 네트워크 필요).
3. 카메라 앞에서 물러나 양손과 패드 6개가 다 보이는 위치를 잡는다.
4. 오른쪽 "타격 감도" 슬라이더를 실제로 쳐 보면서 조정한다 — 너무 낮으면 살짝만 움직여도 소리가
   나고(오탐), 너무 높으면 세게 쳐도 반응이 없다(누락). 기본값 1.8은 추정치라 웹캠·조명·팔 길이에
   따라 다시 맞춰야 한다.
5. "마스터 볼륨"으로 소리 크기를 조절한다 (이어폰 사용 시 특히 유용).
6. BPM을 정하고 메트로놈을 켠 뒤 패드를 치면, 로그 표에 각 히트가 박자보다 몇 ms 빠르거나 늦었는지
   기록된다. "온비트율(±100ms)"이 정확도 지표다.

## 설계에서 정한 것

- **손끝(landmark 8)을 추적점으로 사용**: 손목(0)보다 진폭이 커서 손목 스냅 동작의 속도 신호가
  뚜렷하다. 대신 손가락을 접었다 펴는 동작에도 반응할 수 있어, 정말 "치는" 동작인지는 순수하게
  속도만으로 판단한다(모양은 안 봄).
- **rising-edge + 쿨다운**: 임계값을 넘은 첫 프레임에서만 히트로 잡아서, 손을 오래 빠르게 흔들어도
  한 번만 세도록 했다. 쿨다운 150ms는 진동/떨림으로 인한 재트리거를 추가로 막는 안전장치다.
- **패드 사이 중립 구간**: 스틱을 되돌리는 동작이 다른 패드를 잘못 건드리지 않도록 위·아래 패드
  사이에 히트가 안 나는 빈 띠를 뒀다.
- **오디오는 전부 합성**: 샘플 파일을 안 쓰면 저장소 용량도 안 늘고, 라이선스 문제도 없고, 코드만
  보면 소리가 왜 그렇게 나는지 바로 이해된다 — "블랙박스 모델을 가져다 쓰는 대신 이해할 수 있는
  부분은 직접 만든다"는 이번 5일 과제의 취지에도 맞는다.

## 알려진 한계 (수 ~ 목 개선 대상)

- **감도 임계값(1.8)은 검증되지 않은 초기값**이다. 이 환경엔 웹캠·GPU가 없어 실제 웹캠으로 튜닝하지
  못했다 — 반드시 실제 사용 환경에서 슬라이더로 다시 맞춰야 한다.
- 손 인식 결과의 배열 순서(핸드 인덱스)는 프레임 간 안정적으로 보장되지 않는다 — 두 손이 겹치거나
  한 손이 잠깐 사라지면 왼손/오른손 라벨이 뒤바뀔 수 있다.
- 카메라가 좌우 반전(거울 모드)이라 핸드니스(Left/Right) 라벨이 실제와 반대로 보일 수 있다 —
  로그의 "손" 열은 참고용으로만 볼 것.
- 발 페달(킥 드럼)을 흉내 내지 않는다 — 킥도 손으로 친다. 진짜 두 발 킥 페달을 넣으려면 자세
  추정(Pose)이 추가로 필요하다.
- 오디오 지연(스피커/블루투스 헤드폰 레이턴시)을 보정하지 않는다 — 무선 이어폰을 쓰면 온비트율
  수치가 실제 타이밍보다 나쁘게 나올 수 있다.
